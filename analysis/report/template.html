Precision under saturation: what weight and KV-cache quantization actually change in vLLM

Performance mode. Four precision arms of Qwen3.6-35B-A3B serve the identical 1,000-request PubMed workload replayed against the identical Azure arrival trace. Everything except weight precision and KV-cache dtype is held fixed, so every difference below is attributable to precision.

  • model Qwen3.6-35B-A3B · TP = 2 · TRITON_ATTN
  • precision arms w16kv16 (BF16 · BF16 KV) · w8kv16 (FP8 block W8A8 · BF16 KV) · w16kv8 (BF16 · FP8 KV) · w8kv8 (FP8 block W8A8 · FP8 KV)
  • max_num_seqs 256 (all arms)
  • max_num_batched_tokens 32,768 (all arms)
  • workload 1,000 longest PubMed test articles · 8,868.8 mean ISL · 2,434.7 mean OSL
  • arrivals Azure bursty window, 303.1 s, CV ≈ 2.18, replayed unscaled

All four runs completed 1,000 / 1,000 requests with zero failures. Run IDs are dated 2026-08-18; the four arms were executed concurrently as four independent TP=2 replicas, one per GPU pair (HIP 0,1 / 2,3 / 4,5 / 6,7), at Git commit 71788d5. Every chart below is drawn live from the run artifacts — hover to read values.

1 Goal

The research question the harness exists to answer:

Research question How does vLLM inference behavior change when model-weight and KV-cache precision change, and which scheduler, KV-cache, latency, or HBM effects explain the performance difference?

Two commitments follow from that phrasing and shape everything below. First, the object of study is behavior over time, not a single throughput number — so every arm records complete timestamped runtime series (arrivals, completions, per-request TTFT and TPOT, running and waiting requests, preemptions, KV-cache occupancy and capacity, and four-GPU HBM traffic) rather than only its final aggregates. Second, the question asks for a mechanism, not a ranking: it is not enough to observe that one arm is slower, the scheduler, cache-capacity, or memory-bandwidth effect that produces the difference has to be identifiable in the telemetry.

This report covers Part 1 performance mode only. Accuracy mode (GPQA Diamond, LiveCodeBench) and the Part 2 PyTorch Profiler kernel study are separate and deliberately excluded — full-run profiling is never enabled during Part 1, because it would perturb the very timings being measured.

2 What to observe

Three groups of measurements, stated before the results so the reading stays honest.

1 · End-to-end metrics
  • TTFT — queue wait + prefill. Does precision touch it at all under a saturating burst?
  • TPOT — steady-state decode, where dequantization and KV reads happen every step. Do the two quantization axes each move it, and do they compound?
  • Token throughput — does the extra cache convert into work done, or only into residency?
  • Throughput against latency — is there a trade-off at all, or does one arm dominate? Plotted as Pareto charts in §5.1: throughput vs TTFT and throughput vs TPOT.
2 · KV cache and scheduler behaviour
  • KV utilization — how much cache each precision buys, and whether it stays pinned at 100 % (cache-bound) or falls away from it (something else binds).
  • Running requests — is the extra cache spent on batch width, and does max-num-seqs=256 become the limiter instead of the cache?
  • Waiting requests — backlog drain rate; the slope is the real throughput signal.
  • Preempted requests — scheduler thrash. More cache should mean fewer evictions.
The decisive pattern: capacity up, batch width up, throughput flat would mean quantization buys residency rather than speed.

3 Experiment design performance mode

A four-cell single-factor-pair design. The two quantization axes — weight precision and KV-cache dtype — are crossed to give four arms, and every other variable is pinned. Because both axes are binary, the design isolates each one (w8kv16 moves weights only, w16kv8 moves KV only) and their combination (w8kv8), against an unquantized reference (w16kv16).

MI250 has no pre-tuned FP8 GEMM kernel config for this model's shapes. Unlike an A100 (no FP8 support at all, so w8 would run a fixed weight-only dequant-to-BF16 path), MI250 executes vLLM's genuine block-quantized FP8×FP8 (fp8_w8a8) kernel path for the w8 arms — but every TP worker in both FP8-weight arms logs, for 5 distinct GEMM shapes (confirmed by grepping both runs' server logs: N=6144,K=2048 / N=4608,K=2048 / N=2048,K=2048 / N=2048,K=256 / N=512,K=2048, 10 warning lines total per run across both TP workers): WARNING [fp8_utils.py:851] Using default W8A8 Block FP8 kernel config. Performance might be sub-optimal! Config file not found at .../N=…,K=…,device_name=AMD_Instinct_MI250X_MI250,dtype=fp8_w8a8, block_shape=[128,128].json. No tuned block/tile configuration ships for this device+shape combination, so vLLM falls back to a generic default. This is the single most important design caveat for reading the results: the severe w8 slowdown measured in Section 5 is very likely dominated by this missing, fixable tuning artifact, not an inherent MI250 arithmetic ceiling — a materially different story from an A100's genuine lack of FP8 hardware. (Separately, a MoE-routing kernel config is also missing on every arm, precision-independent — see Section 4.) Names alone are not evidence; runtime server logs and Stage B validation are.

Workload and arrival policy

  • prompts 1,000 longest intact PubMed test articles satisfying the context constraint (selection_policy=longest_prompt_tokens), frozen and hash-pinned
  • arrivals the burstiest selected 1,000-request Azure window — 303.145 s, ≈3.299 req/s mean, inter-arrival CV ≈ 2.182 — replayed at its recorded offsets without scaling
  • reasoning thinking enabled, budget 6,144 tokens (forces the </think> boundary and leaves ≥4,096 tokens for the answer)
  • output cap 10,240 tokens
  • concurrency no client-side semaphore; max-num-seqs=256 alone governs server residency while the trace supplies arrivals

Pairing the longest prompts with the burstiest arrival window is a deliberate stress design: it maximizes KV-cache pressure per request and concentrates arrivals, so cache capacity and scheduler admission become the binding constraints rather than raw compute. That choice is what makes the precision axis legible — and, as Section 5 shows, it also drives the system deep into saturation.

The Azure arrival window 1,000 requests · 303.145 s · replayed unscaled

The window was selected by retaining the 10 % shortest-duration candidate windows, maximizing the population CV of the 999 inter-arrival times, then breaking ties by shorter duration and earlier source position. This is the entire input signal: all four arms receive these exact 1,000 offsets.

    source: traces/processed/azure_multimodal_bursty_1000.csv · ARRIVAL_OFFSET_S · sha256 3b487d34…

    Why this window matters The mean rate is only 3.30 req/s, but the arrivals are nowhere near uniform: the busiest single second carries 19 requests (5.8 × the mean) and the busiest 10 s carries 96, while four gaps exceed 5 s and the longest is 8.90 s. That is what an inter-arrival CV of 2.18 looks like. The cumulative curve shows the shape has two bursts rather than a steady ramp: 25 % of the workload lands in the first 35 s, the middle of the window is comparatively quiet, and then 44 % arrives in the final 60 s (22 % in the final 30 s alone, with the densest 10 s starting at t = 251 s). The queue is therefore being filled hardest at the exact moment the trace ends, which is why the backlog in Section 5.4 peaks just after 303 s and then takes hours to drain.

      5.1 Throughput against latency one point per arm · up and to the left is better

      source: serving_metrics per arm · filled marker = Pareto-optimal · hollow = dominated (another arm is both faster and higher-throughput)

      Observations There is no trade-off to make at all on this hardware. w16kv16 is the sole Pareto-optimal point in all 24 of 24 throughput × latency × statistic combinations — simultaneously the highest-throughput and the lowest-latency arm, every time, leaving the other three strictly dominated with no exception (on the earlier A100 measurement of this same design, one combination — p50 TTFT — had a marginal exception; here there is none). Quantization does not buy a different point on a frontier; it moves the system down and to the right.
      • vs TPOT the spread is extreme and ordered — the four arms string out over 46.6 → 778.4 ms mean, a 16.7 × range, while total throughput falls only 2.3 × (3,074.6 → 1,314.7 tok/s). Most of the movement is horizontal: cost far out of proportion to any throughput change. w16kv16 dominates at every statistic, tail included (p99 53.3 → 1,192.4 ms).
      • vs TTFT the points do not collapse into a cluster the way they did on A100. Mean TTFT spans 1,723.3 s to 3,826.1 s — a 122 % spread, comparable in relative size to the TPOT spread, because on this hardware the two FP8-weight arms are so much slower per request that their queues drain far more slowly too. TTFT here is not precision-invariant; it inherits the same ordering as TPOT.
      • The KV-only axis is nearly free; the weight axis is not. w16kv8 (KV8 alone) sits only 1.8 % behind w16kv16 on total throughput and second-closest on every latency statistic — a real but modest cost. w8kv16 (weights alone) loses 57 % of total throughput and pays a 15.1 × TPOT-mean penalty for the same single-axis change. The two axes are not comparable in cost on MI250, unlike the roughly symmetric ≈ 1.8 × penalty each axis paid independently on A100 — see §5.4 for why (the missing tuned FP8 GEMM kernel config only affects the weight axis).

      5.3 TTFT CDF per-request time to first token · n = 1,000 per arm · left is better

      source: raw/per_request.csv · ttft_s · red guides are the borrowed interactive (2 s) and server (3 s) P99 TTFT SLOs

      Observations Read the axis first: it runs to roughly 7,400 s ≈ 2.1 hours. That is not a plotting artifact. 1,000 requests arrive inside a 303 s window, but even the fastest arm needs 3,675 s to serve them — 12.1 × the arrival window — so almost every request spends most of its TTFT sitting in the backlog.
      • Unlike the A100 measurement, precision is clearly visible here — TTFT follows the same weight-precision split as TPOT. Mean TTFT is 1,723.3 s / 1,815.9 s for the BF16-weight arms versus 3,826.1 s / 3,734.6 s for the FP8-weight arms — roughly double, not a 4.6 % spread. Because the FP8-weight arms decode so much slower per request (§5.2), their queues also drain more slowly, so TTFT inherits the same split even though TTFT itself measures queue wait, not decode speed.
      • Within each cluster the ordering is tight: w16kv16 vs w16kv8 differ by only 5.4 % on mean TTFT, and w8kv16 vs w8kv8 by only 2.5 % — consistent with §5.1's finding that the KV axis alone costs little compared to the weight axis.
      • Both FP8-weight arms show a genuine multi-hundred-second plateau, not just w8kv8: w8kv16 has a 928 s gap with no first token issued between roughly t = 911 s and t = 1,839 s (at CDF ≈ 0.19), and w8kv8 has a 773 s gap between t = 1,355 s and t = 2,129 s (at CDF ≈ 0.26). Both align with the point where that arm's running-requests line saturates against max-num-seqs=256 in the timeline below — the scheduler admits a large cohort at once and then has no free slot until that cohort's (very slow) decode drains. Switch the x scale to log to see both isolated from the bulk of the distribution.
      Against the borrowed SLOs, every arm still fails the P99 TTFT target by orders of magnitude — p99 TTFT of 3,250.7–7,340.1 s against a 2–3 s target — even though the BF16-weight arms' TPOT now clears or nearly clears its own SLO (§5.2). TTFT here is dominated by this workload's 12×-oversubscribed queue, not by precision; that part of the A100 finding still holds.

      5.4 Stacked timeline six panels, one shared clock, all four arms overlaid

        source: plot_data.json · 500 ms bins re-binned to 5 s · running-requests band spans the within-bin minimum to mean, so preemption churn stays visible

        Observations — this is where the mechanism shows
        • FP8 weights buy far more cache on MI250 than weight-only Marlin did on A100. Runtime capacity goes 428,584 → 3,149,889 → 849,427 → 6,202,042 tokens (w16kv16 / w8kv16 / w16kv8 / w8kv8) — w8kv8 holds 14.5 × the reference cache, roughly 4 × the capacity multiplier the A100 measurement found (3.84 ×). MI250's genuine FP8×FP8 storage frees far more HBM than A100's weight-only-dequant path did, and an FP8 KV cache still separately roughly doubles per-token cache cost efficiency.
        • Whether that cache converts into batch width depends on which limiter binds. For the two BF16-weight arms, effective concurrency (capacity ÷ mean ISL+OSL) is 37.9 and 75.2 — comfortably under max-num-seqs=256 — and w16kv16's observed peak running requests (38) tracks its effective concurrency almost exactly, confirming the cache genuinely is the limiter there. w16kv8's peak (58) falls short of its 75.2 ceiling, so the burst arrival pattern, not cache capacity, is the binding constraint for that arm specifically. For the two FP8-weight arms, effective concurrency (278.4 and 548.6) exceeds 256 — both hit the scheduler cap directly, running pinned at exactly 256 for most of the trace.
        • Total throughput does not decline smoothly with more quantization — it splits in two, matching §5.1/§5.2. Total token throughput is 3,074.6 / 1,321.7 / 3,018.0 / 1,314.7 tok/s: the two BF16-weight arms cluster near 3,000–3,075 tok/s, the two FP8-weight arms near 1,315–1,322 tok/s — a 2.3 × gap between clusters and almost no gap within one. Wall-clock duration follows the same split (3,675 s / 8,560 s / 3,742 s / 8,600 s). This is not the smooth monotonic decline the A100 measurement showed across all four arms; on MI250 the KV axis alone barely moves throughput, and the weight axis alone moves it by more than half.
        • Preemptions still trend down with cache size, though not perfectly monotonically: 161 → 111 → 119 → 0. w8kv8 (the largest cache, 14.5 ×) suffers zero preemptions across the entire run — the cleanest result in the whole report — while w8kv16 (7.35 ×) has fewer than the reference despite pairing FP8 weights with an unquantized KV cache. This axis is a genuine, unambiguous win for more cache regardless of precision.
        • KV utilization confirms which arms are cache-bound. Mean KV occupancy is 96.8 % / 87.8 % / 95.9 % for the three smaller-cache arms (all three do reach 100 % at some point in the run) but only 61.6 % for w8kv8, which never exceeds 85.8 % occupancy at any point — its 14.5 × cache is large enough that the max-num-seqs=256 scheduler cap binds well before the cache does, so the arm cannot spend the rest of its capacity on anything.
        • No arm is anywhere near HBM-bandwidth-bound, and — unlike A100 — utilization tracks throughput directly rather than falling with quantization. Mean combined (read+write, this hardware cannot separate them — see §4) bandwidth utilization is 32.1 % / 5.3 % / 23.6 % / 4.1 %, i.e. highest for the fastest arms and lowest for the slowest ones, simply because a slower arm moves less data per second. The ceiling on MI250 is not memory bandwidth in any arm.
        Synthesis — and this inverts part of the A100 conclusion. On A100, weight and KV quantization of Qwen3.6-35B-A3B were capacity optimizations, not speed optimizations, for a structural reason: the A100 has no FP8 tensor cores at all, so weight-only Marlin dequantization is the only path available and permanently pays a fixed, unavoidable cost. On MI250 the story is different in kind. KV-cache quantization alone is close to free here — see §5.1/§5.2 — and, combined with genuine FP8 weight storage, buys dramatically more cache (14.5 × vs A100's 3.84 ×) with a real, near-total elimination of preemptions. The severe cost sits entirely on the weight axis, and — unlike A100 — the evidence points to a fixable cause rather than a hardware ceiling: every FP8-weight worker logs that vLLM found no tuned block-quant GEMM kernel config for this exact (device, shape) combination on MI250 and fell back to a generic default (§3). MI250 does execute genuine FP8×FP8 arithmetic for these arms — it is not doing A100's forced dequant-to-BF16 path — so there is no structural reason it should cost 15–17 × in TPOT rather than something much closer to the KV-only axis's modest premium. Whether tuning that kernel config would close most of this gap, and whether MI250's actual FP8 arithmetic ceiling then looks more like A100's "capacity, not speed" story or something else entirely, is an open, testable follow-up (§5.6) — this report's data supports the caveat, not yet the answer.

        5.6 Workload identity check the arms must be serving the same work

        source: raw/per_request.csv · prompt_len / output_tokens

        Control The ISL curves are exactly coincident — the four arms replay byte-identical prompts, so any single curve hides the other three. That is the control that licenses attributing every difference above to precision. The OSL curves separate only slightly (sampling changes generation lengths), which is the 0.9 % output-token spread quoted in Section 4 — far too small to explain a 16.7 × TPOT-mean difference.
        Scope of these conclusions. They hold for this hardware (8 × AMD MI250, TP=2 per replica, TRITON_ATTN), this model, and this deliberately saturating workload — long prompts, bursty arrivals, max-num-seqs=256. Two concrete, testable follow-ups fall directly out of this run: (1) the missing FP8 GEMM kernel config (§3, §5.4). Generating a tuned block/tile configuration for this device+shape via vLLM's kernel autotuning benchmark, then re-running w8kv16/w8kv8, would separate "MI250 FP8 weights are inherently this much slower" from "an untuned kernel made them look that way" — the evidence here supports the latter but does not yet measure how much of the gap it closes. (2) the scheduler cap now binds two arms, not one. Both w8kv16 (effective concurrency 278) and w8kv8 (549) exceed max-num-seqs=256, so neither arm's full cache advantage is testable at this setting — an unsaturated arrival rate, or a higher max-num-seqs, would let some of that unused capacity show up as admitted load instead of being capped away. Until both follow-ups run, treat the size of the FP8-weight penalty as an upper bound, not a hardware ceiling.
