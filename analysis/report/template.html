Precision under saturation: what weight and KV-cache quantization actually change in vLLM

Performance mode. Four precision arms of Qwen3.6-35B-A3B serve the identical 1,000-request PubMed workload replayed against the identical Azure arrival trace. Everything except weight precision and KV-cache dtype is held fixed, so every difference below is attributable to precision.

  • model Qwen3.6-35B-A3B · TP = 4 · FLASHINFER
  • precision arms w16kv16 (BF16 · BF16 KV) · w8kv16 (FP8 Marlin · BF16 KV) · w16kv8 (BF16 · FP8 KV) · w8kv8 (FP8 Marlin · FP8 KV)
  • max_num_seqs 256 (all arms)
  • max_num_batched_tokens 32,768 (all arms)
  • workload 1,000 longest PubMed test articles · 9,412 mean ISL · 2,437 mean OSL
  • arrivals Azure bursty window, 303.1 s, CV ≈ 2.18, replayed unscaled

All four runs completed 1,000 / 1,000 requests with zero failures. Run IDs are dated 2026-08-17; every arm was executed sequentially at Git commit 6a63000. Every chart below is drawn live from the run artifacts — hover to read values.

1 Goal

The research question the harness exists to answer:

Research question How does vLLM inference behavior change when model-weight and KV-cache precision change, and which scheduler, KV-cache, latency, or A100 HBM effects explain the performance difference?

Two commitments follow from that phrasing and shape everything below. First, the object of study is behavior over time, not a single throughput number — so every arm records complete timestamped runtime series (arrivals, completions, per-request TTFT and TPOT, running and waiting requests, preemptions, KV-cache occupancy and capacity, and four-GPU HBM traffic) rather than only its final aggregates. Second, the question asks for a mechanism, not a ranking: it is not enough to observe that one arm is slower, the scheduler, cache-capacity, or memory-bandwidth effect that produces the difference has to be identifiable in the telemetry.

This report covers Part 1 performance mode only. Accuracy mode (GPQA Diamond, LiveCodeBench) and the Part 2 PyTorch Profiler kernel study are separate and deliberately excluded — full-run profiling is never enabled during Part 1, because it would perturb the very timings being measured.

2 What to observe

Three groups of measurements, stated before the results so the reading stays honest.

1 · End-to-end metrics
  • TTFT — queue wait + prefill. Does precision touch it at all under a saturating burst?
  • TPOT — steady-state decode, where dequantization and KV reads happen every step. Do the two quantization axes each move it, and do they compound?
  • Token throughput — does the extra cache convert into work done, or only into residency?
  • Throughput against latency — is there a trade-off at all, or does one arm dominate? Plotted as Pareto charts in §5.2: throughput vs TTFT and throughput vs TPOT.
2 · KV cache and scheduler behaviour
  • KV utilization — how much cache each precision buys, and whether it stays pinned at 100 % (cache-bound) or falls away from it (something else binds).
  • Running requests — is the extra cache spent on batch width, and does max-num-seqs=256 become the limiter instead of the cache?
  • Waiting requests — backlog drain rate; the slope is the real throughput signal.
  • Preempted requests — scheduler thrash. More cache should mean fewer evictions.
The decisive pattern: capacity up, batch width up, throughput flat would mean quantization buys residency rather than speed.

3 Experiment design performance mode

A four-cell single-factor-pair design. The two quantization axes — weight precision and KV-cache dtype — are crossed to give four arms, and every other variable is pinned. Because both axes are binary, the design isolates each one (w8kv16 moves weights only, w16kv8 moves KV only) and their combination (w8kv8), against an unquantized reference (w16kv16).

A100 has no native FP8 compute. The w8 arms therefore run vLLM's FP8 weight-only Marlin path with BF16 activations — weights are stored at 8 bits and dequantized into the GEMM — not native FP8 tensor-core execution. This is the single most important design caveat for reading the results: on this hardware, w8 buys weight memory, and pays dequantization cost, but cannot buy arithmetic throughput. Names alone are not evidence; runtime server logs and Stage B validation are.

Workload and arrival policy

  • prompts 1,000 longest intact PubMed test articles satisfying the context constraint (selection_policy=longest_prompt_tokens), frozen and hash-pinned
  • arrivals the burstiest selected 1,000-request Azure window — 303.145 s, ≈3.299 req/s mean, inter-arrival CV ≈ 2.182 — replayed at its recorded offsets without scaling
  • reasoning thinking enabled, budget 6,144 tokens (forces the </think> boundary and leaves ≥4,096 tokens for the answer)
  • output cap 10,240 tokens
  • concurrency no client-side semaphore; max-num-seqs=256 alone governs server residency while the trace supplies arrivals

Pairing the longest prompts with the burstiest arrival window is a deliberate stress design: it maximizes KV-cache pressure per request and concentrates arrivals, so cache capacity and scheduler admission become the binding constraints rather than raw compute. That choice is what makes the precision axis legible — and, as Section 5 shows, it also drives the system deep into saturation.

The Azure arrival window 1,000 requests · 303.145 s · replayed unscaled

The window was selected by retaining the 10 % shortest-duration candidate windows, maximizing the population CV of the 999 inter-arrival times, then breaking ties by shorter duration and earlier source position. This is the entire input signal: all four arms receive these exact 1,000 offsets.

    source: traces/processed/azure_multimodal_bursty_1000.csv · ARRIVAL_OFFSET_S · sha256 3b487d34…

    Why this window matters The mean rate is only 3.30 req/s, but the arrivals are nowhere near uniform: the busiest single second carries 19 requests (5.8 × the mean) and the busiest 10 s carries 96, while four gaps exceed 5 s and the longest is 8.90 s. That is what an inter-arrival CV of 2.18 looks like. The cumulative curve shows the shape has two bursts rather than a steady ramp: 25 % of the workload lands in the first 35 s, the middle of the window is comparatively quiet, and then 44 % arrives in the final 60 s (22 % in the final 30 s alone, with the densest 10 s starting at t = 251 s). The queue is therefore being filled hardest at the exact moment the trace ends, which is why the backlog in Section 5.5 peaks just after 303 s and then takes hours to drain.

    Reading the distributions
    • The selection floor is visible. The shortest prompt is 6,511 tokens — there are no short requests at all, which is exactly what selection_policy=longest_prompt_tokens is for. For contrast, the unfiltered 1,000-request PubMed workload records a median of 3,232 prompt tokens in its own manifest (datasets/metadata/pubmed_azure_bursty_1000.json); the longest-selection workload served here has a median of 8,099, roughly 2.5 × larger.
    • ISL is heavily right-skewed — p50 8,099 but p99 28,569 and max 53,967, a 6.7 × spread between median and tail. A handful of very large prefills therefore compete with the whole decode batch, which is a significant contributor to the multi-second ITL tails in Section 5.3.
    • OSL is tightly clustered and nearly arm-invariant — every arm sits at a median of 2,391–2,424 tokens with p99 ≈ 3,370. The 6,144-token thinking budget and 10,240 output cap are almost never the binding constraint; only w16kv16's 6,917-token maximum comes close. The total-output spread across arms is 0.9 %, far too small to explain the 2.8 × TPOT difference.
    • ISL exceeds OSL by 3.9 × on average (9,412 vs 2,437), so this workload is prefill-heavy in token count while being decode-heavy in wall-clock — the asymmetry that makes KV-cache capacity the interesting variable.

      5.2 Throughput against latency one point per arm · up and to the left is better

      source: serving_metrics per arm · filled marker = Pareto-optimal · hollow = dominated (another arm is both faster and higher-throughput)

      Observations There is essentially no trade-off to make. In 21 of the 24 throughput × latency × statistic combinations, w16kv16 is the sole Pareto-optimal point — simultaneously the highest-throughput and the lowest-latency arm, leaving the other three strictly dominated. Quantization here does not buy a different point on a frontier; it moves the system down and to the right.
      • vs TPOT the spread is wide and ordered — the four arms string out over 313 → 874 ms mean while total throughput falls only 1,266 → 1,152 tok/s. Nearly all the movement is horizontal: cost without compensation. w16kv16 dominates at every statistic, tail included (p99 371 → 1,559 ms).
      • vs TTFT the points collapse into a vertical cluster — TTFT varies by 4.6 % across arms while throughput varies by 9 %. TTFT is set by the arrival trace and the drain rate, not by precision, so this panel mostly confirms that the x-axis is the wrong lever to pull.
      • The one exception is p50 TTFT, where w8kv16 is marginally faster (5,120.9 s vs 5,134.2 s) and so joins the frontier for all three throughput measures. That is a 0.26 % latency gain for a 2.6 % throughput loss, on a quantity whose across-arm spread is already smaller than the difference between its own p50 and mean — treat it as noise, not as a real alternative. Select p50 TTFT above to see the second marker fill in.

      5.3 TPOT CDF per-request time per output token · n = 1,000 per arm · left is better

      source: raw/per_request.csv · tpot_s × 1000 · red guides are the borrowed interactive (15 ms) and server (80 ms) TPOT SLOs

      Observations The four curves separate cleanly into three groups, and quantization makes decode slower on this hardware, not faster:
      • w16kv16 is both fastest and tightest — median 327 ms, p99 371 ms, a spread of only 44 ms between p50 and p99. The near-vertical rise is a system in a very regular decode rhythm.
      • The two single-axis arms land on top of each other: w8kv16 median 576 ms and w16kv8 median 590 ms — a 2 % gap, despite changing entirely different things. Each axis alone costs ≈ 1.8 × the baseline median.
      • w8kv8 is worst and least predictable — median 880 ms, p90 1,208 ms, p99 1,559 ms. Its p50→p99 spread is 680 ms, 15 × the baseline's. The two axes compound rather than cancel.
      The ITL tails tell the same story from the other side: median ITL rises 100 → 160 → 162 → 347 ms while p99 ITL sits at 7.7–11.5 s in every arm — those multi-second gaps are preempted requests waiting to be rescheduled. Both SLO guides sit hard against the left axis: even the fastest arm misses the server target by 4 ×.

      5.4 TTFT CDF per-request time to first token · n = 1,000 per arm · left is better

      source: raw/per_request.csv · ttft_s · red guides are the borrowed interactive (2 s) and server (3 s) P99 TTFT SLOs

      Observations Read the axis first: it runs to roughly 9,500 s ≈ 2.6 hours. That is not a plotting artifact. 1,000 requests arrive inside a 303 s window, but the fastest arm needs 9,350 s to serve them — 31 × the arrival window — so almost every request spends most of its TTFT sitting in the backlog.
      • Precision is nearly invisible here. Mean TTFT spans 5,012 s to 5,241 s across all four arms — a 4.6 % spread, against a 2.8 × spread in TPOT. The curves are essentially superimposed because TTFT is dominated by queue wait, and queue wait is set by the arrival trace and the drain rate, not by the arithmetic.
      • The residual ordering still matches the drain rate. w8kv8's curve sits furthest right in the upper tail (p99 9,453 s vs 8,799 s for w16kv16), which is simply its 10 % longer run: the last requests wait for a queue that empties more slowly.
      • The w8kv8 plateau at CDF ≈ 0.23 is a genuine gap — no request in that arm received a first token between roughly 2,300 s and 3,200 s. It aligns with the point where w8kv8's running-requests line saturates in the timeline below, consistent with the scheduler admitting a large cohort at once and then having no free slot until that cohort's decode drains. Switch the x scale to log to see it isolated from the bulk of the distribution.
      Against the borrowed SLOs, every arm fails both by three orders of magnitude — p99 TTFT of 8,799–9,453 s against 2–3 s targets, and a best-case TPOT of 327 ms against 15 ms / 80 ms. That is the expected consequence of a deliberate saturation design, and it means these runs characterize throughput and scheduler behaviour, not SLO attainment.

      5.5 Stacked timeline six panels, one shared clock, all four arms overlaid

        source: plot_data.json · 500 ms bins re-binned to 5 s · running-requests band spans the within-bin minimum to mean, so preemption churn stays visible

        Observations — this is where the mechanism shows
        • KV quantization buys a great deal of cache. Runtime capacity goes 1.09 M → 1.87 M → 2.16 M → 4.17 M tokens, i.e. w8kv8 holds 3.84 × the reference cache. Both axes contribute: FP8 weights free HBM for the cache (1.72 ×) and an FP8 KV halves per-token cache cost (1.98 ×).
        • That cache is converted into batch width, exactly as designed. Mean running requests rise 82 → 137 → 137 → 207, tracking the effective concurrency each cache can sustain (capacity ÷ mean ISL + OSL = 92 / 158 / 182 / 352).
        • But total throughput does not improve — it degrades. Total token throughput falls 1,266 → 1,234 → 1,231 → 1,152 tok/s and wall-clock rises 9,350 → 10,284 s. The waiting-request panel makes it visual: all four backlogs drain along almost the same slope, with w8kv8 the last to reach zero. Same work, more requests in flight, therefore proportionally more time per request — Little's law, and precisely the TPOT ordering in 5.2.
        • Preemptions collapse: 212 → 186 → 169 → 38. This is the one unambiguous win for KV quantization. w8kv8 suffers 5.6 × fewer preemptions than the reference, and its preemption curve is flat after an early step while the other three climb steadily all run long.
        • At w8kv8 the cache stops being the constraint. Its KV utilization is the only one that does not stay pinned at 100 % — it peaks around 2,300–4,500 s and then decays to ≈ 72 %, while its running-requests line sits flat at 256. Its effective concurrency (352) exceeds max-num-seqs=256, so the scheduler cap binds instead. The arm cannot spend the rest of its 3.84 × cache, which is why it converts none of it into throughput.
        • No arm is HBM-bandwidth-bound. Mean bandwidth utilization is only 6.6 % / 5.0 % / 4.7 % / 3.6 % (mean read 83 → 59 → 55 → 38 GB/s), and it falls with quantization. Smaller KV traffic therefore cannot buy speed on this workload — the ceiling is elsewhere: FP8 weight-only Marlin dequantizes into every GEMM, and attention cost grows with batch width.
        Synthesis. On 4 × A100, weight and KV quantization of Qwen3.6-35B-A3B are capacity optimizations, not speed optimizations. They deliver up to 3.84 × KV cache, 2.5 × batch width, and 5.6 × fewer preemptions, while costing 2.7 × per-request TPOT and 9 % total throughput. The reason is structural rather than incidental: the A100 has no FP8 tensor cores, so w8 pays dequantization on every GEMM without any arithmetic return, and the machine is nowhere near bandwidth-bound, so kv8's lighter memory traffic has no ceiling to lift.

        5.7 Workload identity check the arms must be serving the same work

        source: raw/per_request.csv · prompt_len / output_tokens

        Control The ISL curves are exactly coincident — the four arms replay byte-identical prompts, so any single curve hides the other three. That is the control that licenses attributing every difference above to precision. The OSL curves separate only slightly (sampling at temperature > 0 changes generation lengths), which is the 0.9 % output-token spread quoted in Section 4 — far too small to explain a 2.8 × TPOT difference.
        Scope of these conclusions. They hold for this hardware (A100, no FP8 tensor cores), this model, and this deliberately saturating workload — long prompts, bursty arrivals, max-num-seqs=256. A GPU with native FP8 compute would change the w8 arms' arithmetic entirely, and an unsaturated arrival rate would let extra KV capacity show up as admitted load instead of widened batches. The w8kv8 result also suggests a concrete follow-up: because its effective concurrency (352) exceeds the scheduler cap, its cache advantage is untestable at max-num-seqs=256. Re-running that arm at a higher cap would separate "quantization does not help throughput" from "the scheduler cap prevented it from helping".
